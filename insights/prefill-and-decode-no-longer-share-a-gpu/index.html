Prefill and decode no longer share a GPU

By Frank Ribeiro, Jengara · 23 November 2026 · Product and engineering notes

Disaggregated inference runs the two phases of a model request on separate pools of GPUs. One pool reads the prompt and builds the attention cache. Another uses it to generate the answer token by token. The split sounds minor. In production it changes what a GPU fleet can deliver.

Research approach

Jengara reviewed NVIDIA Dynamo documentation, the llm d record at the Cloud Native Computing Foundation, a Rafay production case study, Vultr and Spheron deployment guidance, and an independent interference analysis. Vendor claims are attributed to their publishers.

Two different jobs were sharing one GPU

Prefill processes every input token in parallel and produces the key value cache generation depends on. NVIDIA describes its scaling pressure as input length, prompt reuse and context size. The work saturates compute.

Decode generates one token at a time, reading that cache back on every step, under pressure from concurrency, output length and active cache memory. It is bound by memory bandwidth rather than arithmetic.

On a shared GPU the two jobs interfere. A long prompt arriving while others are mid answer forces a choice: pause generation for everyone already streaming, or fold the heavy pass into their batch and slow every token. An independent analysis found that one long prefill can inflate the time between tokens by 2 to 30 times under realistic bursts. That is what scheduling unlike work as if it were alike costs.

The split is now shipping as standard tooling

NVIDIA Dynamo reached general availability at version 1.0 on 16 March 2026, as a disaggregated serving layer above engines such as vLLM. Its published benchmarks report up to seven times the throughput on DeepSeek R1 on Blackwell hardware. Treat that as a vendor ceiling under its own test conditions, not a planning number.

Days later, on 24 March 2026, IBM, Red Hat and Google donated llm d to the Cloud Native Computing Foundation as a sandbox project, with NVIDIA and CoreWeave among the founding collaborators. Its route differs: native to Kubernetes, routed through the Gateway API Inference Extension, with prefill and decode in separate pod pools that scale on their own.

What early production evidence shows

Rafay reports a Canadian telecommunications operator that moved mixed workloads to disaggregated serving on the same GPUs. Throughput rose nearly 90 percent. Rebalancing the pool ratio for latency sensitive traffic cut the ninetieth percentile time to first token by 81 percent. Volume grew from hundreds of millions of tokens per hour to billions, up more than 350 percent. Vultr guidance puts the ceiling for models above 32 billion parameters at 1.7 times aggregated throughput, with the gain largest where prompts are long and concurrency is high.

The transfer path is the new critical path

Disaggregation replaces interference with a dependency. The decode pool cannot start until the cache built by the prefill pool arrives, and that state is large. NVIDIA moves it with NIXL directly between GPU memory, over NVLink inside a node or RDMA fabrics such as InfiniBand and RoCE between nodes.

NVIDIA is blunt about the consequence. Production deployments across nodes usually require RDMA or an equivalent fast fabric, and the transfer path should be validated first rather than tuned last. Its documentation names the failure modes plainly: missing device plugin resources, pods without the required RDMA requests, and transport errors. A slow fabric can turn the split into a slower system than the one it replaced.

When staying aggregated is still right

The split charges rent in complexity and transfer time. Deployment guidance for llm d puts the added transfer at roughly 5 to 15 milliseconds and finds a single pool can still win below about 20 concurrent requests. Vultr gives the model size version of the same rule: below about 10 billion parameters, transfer overhead outweighs the benefit of separation.

Small models, short prompts, low concurrency and batch work with loose latency targets all argue for one pool. Disaggregation earns its keep where tail latency is a product promise.

How to adopt it in the right order

Measure the two latencies separately before changing anything. Time to first token belongs to prefill. Time per output token belongs to decode. A blended number hides which pool is starving.

Validate the fabric before the framework. Prove cache transfer speed between the actual nodes, with the device plugins and permissions a production pod will carry. Then size the pools from your own prompt mix. The right ratio follows your input to output balance.

Move one workload first. Pick the service where long prompts and live generation collide most often, split it, and compare cost per successful request against the aggregated baseline. Keep aggregated serving for workloads that never justified the split. Both Dynamo and llm d treat it as a supported mode, not a legacy one.

Jengara decision rule

Split prefill and decode when three conditions hold together: the model is large, concurrency is sustained, and tail latency is worth money. Prove the fabric first, size each pool from your own prompt mix, and judge on cost per successful request at a fixed latency target. If any condition is absent, keep one pool.

Executive takeaway

The unit of inference design is no longer the GPU. It is the phase. Fleets that schedule the phases as the different jobs they are extract more work from the same silicon. Fleets that split without a fast fabric pay twice for the lesson.
